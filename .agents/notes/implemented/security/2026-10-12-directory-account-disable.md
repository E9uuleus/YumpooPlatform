# Agent Note: 企业微信同步驱动平台账号停用

Status: implemented

## Problem

通讯录成员资料曾忽略企微账号状态，完整扫描确认离职时也只更新就业状态。结果是公司管理中出现“已离职 / 已启用”，企微禁用但仍在通讯录中的账号则继续保留平台访问。把来源状态直接覆盖到平台账号又可能撤销管理员手动停用，且既有停用事实要求必须关联一个人类执行人，无法真实表示系统同步。

## Decision

[成员资料适配器](../../../../backend/src/main/java/com/yumpoo/platform/identityaccess/infrastructure/wecom/RestClientWeComDirectoryProfileGateway.java) 按[企业微信读取成员合同](https://developer.work.weixin.qq.com/document/path/90196)将 `status=2`（禁用）和 `status=5`（退出企业）映射为平台停用。`1/4` 不主动停用；缺失字段保持既有状态，不推断启用。未知或畸形状态隔离为资料读取失败。就业状态继续由完整通讯录快照的成员存在性维护，企微激活状态不替代就业事实。

停用标志进入资料指纹和同步 staging。V71 增加 staging 列，并只为 `DIRECTORY_ACCOUNT_DISABLED`、`DIRECTORY_SNAPSHOT_MISSING` 两种系统原因允许停用执行人为空，时间与原因仍必填；普通管理员停用继续保存真实执行人。不会伪造“成员停用了自己”。

[DirectoryAccountStatusService](../../../../backend/src/main/java/com/yumpoo/platform/identityaccess/application/account/DirectoryAccountStatusService.java) 在调用方持有公司治理锁的事务内，仅对 ENABLED 账号执行停用、递增授权版本、撤销全部活动会话、写安全审计及 Outbox。已停用账号保持原执行人、理由和授权版本；重复同步不重复发布停用事件。人工停用和外部停用都不会因下一次企微显示正常而自动启用，启用仍由管理员复核执行。

完整且成功的同步先确认缺失成员离职，再停用本轮与历史已确认离职、仍启用且仍未出现在快照中的企微成员。已有 LEFT 记录的修复不重复制造离职事实或增加本轮离职计数。部分失败、空快照保护及失去租约的同步仍不执行缺失成员对账。外部事实可能使最后一个平台管理员不可用，沿用现有可用性告警和 break-glass 恢复机制。

目录停用发布 `identity.user_account_disabled@2`，原因限定为上述两个目录原因；人工停用继续发布冻结的 v1。项目负责人治理消费者显式订阅 v2，使停用后的负责人缺位继续可见。

## Alternatives considered

- 只把页面上的“已启用”改成“已停用”：无法撤销仍在通讯录中的禁用成员会话，也会造成展示与持久化事实矛盾。
- 将企微正常状态直接映射为 ENABLED：会解除人工安全停用，并可能在返岗时恢复未经复核的访问。
- 用当前同步发起人或目标成员填充系统停用执行人：定时同步不存在该执行人，冒用成员 ID 会污染审计事实。
- 在迁移中批量改写历史账号：缺少最新完整快照与正常事件、会话、审计链路；采用下一次完整成功同步修复。
- 扩展冻结 v1 的固定 ADMIN 原因：破坏旧事件合同；新版本保持明确来源并补齐真实消费者。

## Consequences

部署后需完成一次成功的通讯录同步，历史“已离职 / 已启用”才会补齐。首次同步使用含停用标志的新资料指纹，可能将此前未变化的资料计为更新。返岗或企微重新启用不会自行恢复平台账号，管理员仍需明确启用。

回退到不支持系统停用事实的旧代码前，需要兼容空人类执行人的目录停用记录；不得伪造执行人或删除停用事实以迁就旧约束。

验证覆盖资料状态与指纹、staging 往返、禁用新成员、活动会话撤销、重复同步、历史离职补齐、人工停用保留、部分失败保护及 v2 的负责人治理投影。
