# Agent Note: 从原平台导入工作项

Status: implemented

## Problem

公司要把原协作平台的数据迁入 Yumpoo。原平台能导出 Excel（ID、标题、优先级、状态、处理人、预计结束、父需求、完成工时、需求类别），其中子项标题带缩进，状态有 Yumpoo 没有的取值，处理人是分号分隔的多人，同一标题可以出现多次，父需求都在文件里。

现有创建路径满足不了批量迁入：

- 新建项总是插到项目顶部，并取相邻排序键的中点；连续新建约 120 条后会触发 `PROJECT_ORDER_DENSE`。
- 新建只能从「未开始」开始，且每条都给所有处理人发通知。
- 父项必须先于子项创建；在前端循环调用时，中途失败会留下一半数据。

## Decision

### 入口与流程

- 项目工作项表格的「新增工作项」右侧连一个 ▾，菜单项是「导入工作项」，和按钮一样只在表格视图且有创建权限时出现。
- 三步流程：上传 → 映射列与取值 → 处理重复并预览，确认后提交。支持 .csv、.xlsx、.xls，最大 5 MB、2000 行。
- 文件在浏览器端用 SheetJS 解析，后端不加 Excel 依赖。沿用日历导入与工时导出的先例；浏览器端也能先让用户核对映射再发请求。
- 工作项导入不处理工时：「完成工时」列不可映射。原平台父需求的完成工时是子项之和，直接导入会重复计算；工时由[迁入工时](../architecture/2026-10-28-migrated-time-import.md)单独导入。

### 后端批量接口

`POST /projects/{projectId}/work-item-imports` 带 `dryRun`，需要 CSRF 与 `Idempotency-Key`。预览与提交共用同一个纯函数规划器，提交时重新规划，在单事务内完成；出错的行跳过，其余行照常提交。

与[工作项表格批量操作](2026-09-25-work-item-table-batch-actions.md)的关系：那篇决定「批量操作在前端逐条调用既有单项接口，不新增后端批量端点」，适用于几十项以内、每项都保留自己事件与通知的日常操作，本篇不改变它。导入是数百到两千行的一次性写入，前端逐条调用有上述排序键、初始状态、通知和半途失败四个问题，所以单独走后端接口；两者没有共用代码路径。

- **匹配**：只按标题匹配，trim 后完全相同，范围是本项目内未删除、未归档的工作项。不提供「匹配列」选择，避免用户选错列造成大批量误更新。
- **重复处理**：`CREATE` 全部新增；`SKIP` 命中已有项就跳过；`UPDATE` 恰好命中一个时更新，命中多个记 `MATCH_AMBIGUOUS`，文件内同一标题多行且命中已有项时整组记 `DUPLICATE_IN_FILE`，没有命中就新增。
- **更新语义**：只覆盖 `fields` 里列出的已映射字段，已映射列的空单元格会清空原值。
- **新建的值**：状态直接写入目标状态（不必从「未开始」开始）；排序键用 `ProjectSortKey.evenlySpacedBetween` 一次性给所有新建项分配，按文件顺序排在最前，放不下时整体返回 409 `PROJECT_ORDER_DENSE`；看板 rank 按文件倒序逐条置顶调用既有分配方法，使文件首行排在泳道最上。
- **父项**：按标题先在本次文件的未报错行里查找（被跳过的行视为它命中的已有项），再在项目已有项里查找。父项本身是子项时，挂到它的根祖先下，记 `PARENT_FLATTENED`，所以导入结果总是两级；找不到、匹配到多个、自引用或成环时，新建的行按顶层导入并记对应问题；已有项自己有子项又要变成子项时保持不变。UPDATE 模式下父项为空表示移除现有父项；父项找不到、匹配到多个或成环时保持该项现有的父项不变，只记问题，不会移除。
- **完成时间**：目标状态属于完成类别时，`completedAt` 取导入时刻，不尝试还原原平台的完成时间。
- **事件与审计**：关系和状态直接写入仓储，不发逐条领域事件、不产生通知，整次导入只写一条安全审计，内容是各项数量。所以导入的工作项不出现在项目动态里。

## Alternatives considered

- **前端逐条调用既有接口**：与批量操作 Note 的方式一致，但会触发排序键稠密、全部从「未开始」起步、逐条通知，且父子顺序与半途失败无法处理，已放弃。
- **通过 MCP 导入**：方案复杂、可控性差，预览与映射都没有稳定的位置，放弃。
- **后端解析 Excel**：要新增服务端依赖，且用户无法在提交前核对列映射与取值映射。
- **提供「匹配列」选择**：灵活但容易选错，大批量更新难以撤销；原平台的 ID 与 Yumpoo 的编号也没有对应关系，所以只按标题匹配。
- **一并导入完成工时**：与迁入工时重复计算，也无法处理父需求的汇总值。
- **逐条发事件和通知**：两千行会向处理人批量发送通知，且项目动态被导入记录淹没。

## Consequences

- **导入不可见于动态与通知**：成员不会收到被指派的通知；项目动态里也没有导入记录，追溯只能看那条安全审计。
- **完成时间失真**：已完成项的完成时间都是导入当天，依赖完成时间的统计会把它们算成当天完成。
- **父项被压平**：原平台超过两级的层次会被压成两级，对应行带 `PARENT_FLATTENED` 提示。
- **标题重复的限制**：UPDATE 模式遇到同名多项或文件内重名时不会猜测，调用方只能改用其他模式或先整理文件。
- **相关记录**：与[工作项表格批量操作](2026-09-25-work-item-table-batch-actions.md)并存，导入规模和语义的差别见上文；工时部分见[迁入工时](../architecture/2026-10-28-migrated-time-import.md)。
