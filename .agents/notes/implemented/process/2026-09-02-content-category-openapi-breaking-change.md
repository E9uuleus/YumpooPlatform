# Agent Note: Content 类别重构 OpenAPI 破坏变更闸门

Status: implemented

## Problem

Content 从独立配置工作区收敛为项目级工作项类别目录，需要删除旧 Content 详情、归档、恢复和单 Content 工作项接口，并改变 WorkItem 的创建、列表与详情契约。普通 OpenAPI 兼容检查会正确识别这些变更为破坏性，但直接关闭检查会同时掩盖本次范围之外的契约漂移。

## Decision

`tools/openapi/breaking-change-exceptions.json` 中的类别重构条目只登记此次变更前后规范的精确 SHA-256、原因和本 Note。兼容检查仅在历史基线和当前规范同时匹配这一对哈希时放行；任一侧哈希不同都继续执行严格兼容检查。因此，本次清单不能授权额外契约变化。

当该变更合入 `dev` 后，后续检查提取到的新基线与当前规范相同，脚本不使用例外并恢复普通严格检查。清单保留为可审计的一次性决策记录，不作为未来破坏变更的通配规则。

## Alternatives considered

- 全局关闭或弱化兼容检查：会让无关破坏变更混入同一提交，拒绝。
- 按 operationId 或路径维护宽泛允许列表：难以覆盖 schema 的间接变化，也可能长期误放行，拒绝。
- 提升 API 主版本并长期并存旧接口：当前产品明确不保留旧页面与重定向，维护双轨契约没有收益，拒绝。

## Consequences

- 使用该次例外时，前后规范必须保持条目记录的精确字节；后续规范不能沿用该授权。当前规范与历史授权的分工由 [CI 与 PR 门禁决定](2026-09-08-ci-pr-reliability.md) 接管，正常兼容演进不要求刷新历史哈希。
- CI 验证清单结构、唯一 ID/哈希对、原因和活动 Agent Note 链接，代码生成仍须与当前规范一致。既有条目保持历史完整性；新破坏变更须有明确决策。类别专项保留历史条目，不再要求当前规范有同一旧基线的最新哈希。
- 合并后基线相同时，严格兼容检查自然恢复；无需临时分支条件或人工关闭门禁。
