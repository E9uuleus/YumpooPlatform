# Agent Note: PR 发布说明与分层 Release 描述

Status: implemented

## Problem

服务端与桌面草稿 Release 的正文原来直接罗列非合并提交的标题，存在以下问题：

- **内部写法直接外露**：标题按提交规范带 `type(scope):` 前缀和 `(BF-1～8)` 一类步骤编号，原样出现在 Release 正文、桌面下载页和设置页里。
- **桌面范围不准**：桌面条目按改动路径（`desktop/`、`packages/preload-contract`）筛选，既漏掉落在 Web 页面里的桌面功能，也只读取一页历史。
- **发布决策信息不全**：正文不标迁移是否只扩展，也不写回退能力；部署引擎改动和需要管理员做的主机操作只能另找来源。
- **缺漏无人发现**：合并提交被丢弃，晋升与热修复的摘要进不了正文；也没有任何机制检查发布说明是否缺失。

## Decision

**来源**

- 每个 PR 正文都有且只有一个 `## 发布说明` 段，每行写一条 `- 类别｜范围：描述`。
  - 类别：新增、改进、修复、安全、运维。前四类面向使用者；运维只写给管理员，例如发布顺序或主机操作。
  - 范围：Web、桌面、服务端。
  - 没有可见影响、也没有运维影响时，只写一条 `- 无`。
- 分隔符接受全角和半角，输出统一为全角。
- 描述须为 5–120 字，每个 PR 最多 10 条。
- 描述中不得出现步骤编号、`type(scope):` 前缀、commit SHA 或 `#123`。PR 号由生成器自动附加。
- 模板中的 HTML 注释不参与解析；段内除条目外的任何内容都算错误。
- 解析器 [release-notes.mjs](../../../../tools/release/release-notes.mjs) 由 PR 检查与草稿生成共用。

**严格程度：PR 阶段阻断，草稿阶段只标注**

- [Release Notes Policy](../../../../.github/workflows/release-notes-policy.yml) 检查所有指向 `dev`、`main` 的 PR，修改正文也会触发重新检查。
  - 豁免三类 PR：Dependabot、`backmerge/*`、`dev → main` 晋升。
  - `hotfix/*` 不豁免。
- 生成草稿时，用 `GET /commits/{sha}/pulls` 反查每个非合并提交对应的已合并 PR，每个 PR 只计一次，按提交顺序排列。
  - 有多个候选 PR 时，优先取非豁免的 PR。
  - 以下情况不让草稿失败，而是列入「发布信息 › 未提供发布说明」并写入工作流摘要：没有对应 PR、PR 缺段或格式不合格、提交只经晋升或回合并进入。原因是 PR 检查之前合入的旧 PR 无法补救，而上线决定本就由人在草稿上做。
- 草稿未发布时，每次重跑都重新生成正文。补写 PR 正文后重跑工作流即可刷新；手改的草稿正文会被覆盖。

**正文结构（服务端与桌面相同）**

1. 摘要行：新增、改进、修复、安全四类的条数，以及是否需要管理员操作。
2. 「更新内容」：按类别分组，每条格式为 `范围｜描述（#PR）`。
3. 「升级影响」：
   - 服务端列出：逐个新增迁移的分类（由发布提交本身的迁移清单与例外登记判定只扩展或破坏性）、API/事件契约变化、`deployment/windows/cd/` 引擎改动、运维条目、回退能力（可用 Server Rollback 回退到上一 tag，或因破坏性迁移不能快速回退）。
   - 桌面只列运维条目，以及「只能前滚」。
4. 「发布信息」：来源提交、上一版本、对比范围、指定 attempt 的 CI 链接、包含的 PR、依赖更新、未提供发布说明的项。
5. 桌面另有「发布前试装」清单。

**桌面范围**

- 桌面草稿收集上一已发布 `desktop-v*` 到本提交之间所有 PR 的条目，只取范围为「桌面」的条目，不再按路径筛选。
- `release.json` 的 `notes` 只含面向使用者的桌面条目，格式为 `类别：描述`，最多 20 条。
- `release.json` 的 schema 保持 v1，已部署的下载页无需改动。上传后不再替换。

## Alternatives considered

- **规范化提交标题**：只需去掉前缀和步骤编号，不改流程。但标题仍然是写给开发者的，无法区分范围和管理员操作，也不能校验。
- **变更片段文件（`.changes/*.md`）**：每个 PR 附一个片段文件，发布时汇总。但在 dev/main 双线和回合并之下，什么时候删、由谁删都很难处理。
- **PR 标签加 GitHub 自动生成说明**：分类粗，描述仍是 PR 标题，标签漏打也不会失败。
- **草稿阶段也阻断**：旧 PR 和 Dependabot 会让草稿生成失败；而上线决定本来就在草稿上做，标注出来已经足够。
- **改用 `git log` 取提交**：可以避开 compare API 250 个提交的上限，但桌面草稿需要完整检出历史；单次发布达到上限时正文会提示截断，因此保留 compare API。

## Consequences

- 每个 PR 都要写面向使用者的文字。内部改动写 `- 无`，Release Notes Policy 必须加入 `Protect dev` 与 `Protect main` 的 required checks 才会真正阻断合并。
- 草稿生成多了按提交查 PR 的 API 调用，Prepare Release 与 Prepare Desktop Release 的草稿任务因此需要 `pull-requests: read`。
- 切换前合入的 PR 没有发布说明段，首个新格式草稿会把它们列为未提供。
- 迁移分类依赖发布提交的检出内容；检出缺少迁移文件时，正文提示以发布包内 `windows/release-metadata.json` 为准。
- 提交标题分组仍用于晋升 PR 的汇总评论。
