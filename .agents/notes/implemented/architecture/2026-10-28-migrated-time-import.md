# Agent Note: 迁入工时分类与导入

Status: implemented

## Problem

原协作平台只有一张工时表：行是成员，列是日期，单元格是当天的小时数，没有开始和结束时间。Yumpoo 的工时是带时段的计时记录，份额分摊、GAPS 空档、`/me/timesheet`、团队工时表与加班统计都建立在时段上。

迁入这些历史工时需要：

- 管理员替成员写入。现有写入路径只允许本人写自己的工时。
- 记录不能让成员误当成真实的工作时段去编辑，也不能与成员已有的记录混在一起无法区分。
- 重复迁入同一份数据不能累加。

## Decision

### 迁入工时分类

`TimeCategory` 增加第 5 个固定分类 `MIGRATED`（迁入工时），沿用[非项目固定分类工时](2026-10-22-non-project-time-categories.md)的会话与份额结构，因此份额分摊、GAPS 空档、`/me/timesheet`、团队工时表的 `categoryEntries` 与加班统计都不需要新的读取路径，界面上的标识也直接由分类得出。

- **只读、不可选**：只能由迁入接口写入，成员不能选择它开始计时、补录或改归属，也不能修改、删除或把它作为改归属的来源；它不进入分类选择列表。
  - 开始、切换、补录条目、改归属的目标遇到它返回 422 `TIME_CATEGORY_RESERVED`；修改、删除或把它作为改归属的来源返回 409 `MIGRATED_TIME_READ_ONLY`。
  - `GET /me/time-sessions` 中它的 `canEdit` 为 false，REPLACE 补录的可编辑集合排除它。
- **可选关联项目**：导入时可以统一关联一个 ACTIVE 状态的项目，沿用分类记录的 `category_project_id`。
- **展示**：个人工时日历、我的一天和团队工时表把它标为「迁入工时」，并说明排出的时段不代表实际工作时间。

### 导入接口

`POST /company/migrated-time-imports` 带 `dryRun`，需要 CSRF 与 `Idempotency-Key`，只有公司管理员可用，权限口径与团队视图一致。请求是 `(userId, workDate, minutes)` 的列表，按成员姓名匹配成员发生在前端，后端只收用户 ID。

- **按「成员 × 日」覆盖**：同一成员同一天再次导入，先删除当天开始的旧 `MIGRATED` 记录再写新的，结果是覆盖而不是累加；`minutes = 0` 表示清除当天已有的迁入工时。
- **排布规则**（按公司时区）：从成员的上班时间（没有设置时取默认 09:00）开始，到当天 24:00 为止，把时长依次排进当天的空档。已占用时段是该成员所有未删除的会话，正在运行的会话视为占用到当天结束，当天开始的旧 `MIGRATED` 会话除外。比 `min(15 分钟, 剩余时长)` 短的空档跳过。排不下的一天记 `NOT_ENOUGH_FREE_TIME`，当天不写入任何记录。末段超过下班时间记警告 `PAST_WORKDAY_END`，日期不早于公司时区今天记 `FUTURE_DATE`，当天原有迁入工时被替换记 `REPLACES_PREVIOUS`。
- **事务与并发**：单事务内按用户 ID 排序依次锁定成员的计时状态，先软删除旧记录再插入新记录，每个成员重建一次份额。预览与提交共用同一个纯函数排布器。
- **事件与审计**：不发领域事件，整次导入写一条安全审计，内容是汇总数字。
- **失败不动旧数据**：成员无效（`USER_INVALID`）或排不下的一天不写入也不删除，当天原有的迁入工时保持不变；整次导入的 `categoryProjectId` 不是本公司 ACTIVE 项目时返回 422。
- **公司时区**：workitem 模块不能依赖 organization，控制器通过 workitem 自己的 `CompanyTimeZonePort` 取公司时区，由 reporting 模块用公司配置实现。

### 回退

数据库迁移 V84 扩展了 `ck_work_item_time_session_subject` 与 `ck_work_item_time_share_subject` 的取值，属于 breaking 迁移，在 `contracts/migrations/rollback-safety-exceptions.json` 登记例外，晋升到 `main` 的 PR 须加 `release:breaking-migration` 标签。回退到旧版本前必须先删除 `time_category = 'MIGRATED'` 的会话与份额记录，否则旧版本解析枚举会失败。

`TimeCategory` 响应枚举的扩展会被 openapi-diff 判为不兼容，已在 `tools/openapi/breaking-change-exceptions.json` 按精确哈希登记，本记录是它的依据。

## Alternatives considered

- **在现有分类上加「来源」标记而不新增枚举值**：不需要 CHECK 与枚举扩展，但所有读写路径都要多一个条件判断，只读规则也要散落在各处；而新增分类可以直接复用分类这一套已有机制。
- **独立的迁入工时表**：与份额分摊、GAPS 空档和各类报表要重复一套读取逻辑，团队工时表也要多一路合并。
- **以成员本人身份写入普通分类**：成员能修改或删除这些记录，也无法区分是否为迁入数据，重复迁入时无法精确覆盖。
- **只写日汇总、不排时段**：现有统计依赖时段，要另建日汇总读取路径，并绕过 GAPS 与重叠校验。
- **允许超过当天的排布（跨日顺延）**：会把工时写到没有给出的日期，所以排不下的一天直接报错，不写入。

## Consequences

- **时段是虚构的**：排出的时段只是为了复用现有统计，不代表实际工作时间，所以界面必须标注；其间也会占用成员当天的空档，后续补录的 GAPS 不会再落在这些时段里。
- **回退成本**：这次发布不能用 Server Rollback 快速回退，运维须先清除迁入记录。
- **不留动态**：迁入不发领域事件，也不进入项目活动或「我的动态」，追溯只能看安全审计。
- **项目口径**：与其他分类一样，迁入工时不计入项目统计页；关联项目后出现在团队「项目工时」。
- **覆盖粒度是整天**：不支持只改某一段；需要调整时重新导入当天的总时长。
- **相关记录**：本记录扩展[非项目固定分类工时](2026-10-22-non-project-time-categories.md)，其余约束不变；工作项部分见[导入工作项](../product/2026-10-28-work-item-import.md)。
