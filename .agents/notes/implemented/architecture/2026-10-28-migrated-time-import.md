# Agent Note: 迁入工时导入

Status: implemented

## Problem

原协作平台导出的「工时花费报表」第一个工作表是汇总（行是成员、列是日期），之后每位成员一个明细工作表，每行是成员某天在某个工作项上花费的工时（责任人、日期、ID、标题、花费工时、所属项目），没有开始和结束时间。Yumpoo 的工时是带时段的计时记录，份额分摊、GAPS 空档、/me/timesheet、团队工时表、项目统计与加班统计都建立在时段上。

迁入这些历史工时需要：

- 管理员替成员写入。现有写入路径只允许本人写自己的工时。
- 记录不能让成员误当成真实的工作时段去编辑，也不能与成员已有的记录混在一起无法区分。
- 重复迁入同一份数据不能累加。
- 工时要记到对应的项目和工作项上，项目统计与工作项工时才完整。

## Decision

### 记录

- **记到工作项上**：迁入行写成普通的工作项计时记录（带项目与工作项、无分类、`source='MANUAL'`），并带 `migrated=true` 标记（V86 新增列，默认 false）。份额分摊、项目统计、工作项工时与团队工时表都直接计入，不需要新的读取路径。
- **只读**：带标记的记录与 `MIGRATED` 分类记录同样只读（`Session.migratedImport()`）。`GET /me/time-sessions` 与工作项计时记录中 `canEdit` 为 false、`migrated` 为 true；修改、删除或作为改归属的来源返回 409 `MIGRATED_TIME_READ_ONLY`；REPLACE 补录不裁剪它们。
- **`MIGRATED` 分类保留给首版记录**：首版迁入写成的分类记录照常只读显示，导入不再写这个分类；同一成员同一天重新迁入时，两种旧记录都随这一天整天覆盖。分类的「保留、不可选择」规则不变。
- **展示**：「我的一天」画成斜线底纹的只读卡片并注明不代表具体时段；团队工时表和「我的工时」依据 `TeamTimesheetEntry.migratedDurationMs`（由份额关联记录标记统计）和 `MIGRATED` 分类给格子加「迁」角标；工作项计时记录标注「迁入工时」。

### 导入接口

`POST /company/migrated-time-imports` 带 `dryRun`，需要 CSRF 与 `Idempotency-Key`，只有公司管理员可用。文件在浏览器端解析（只读含明细表头的工作表，合并的责任人与日期沿用上一行），按姓名匹配成员也在前端；请求是按文件顺序的 `(userId, workDate, projectName, workItemTitle, minutes)` 行。

- **匹配**（后端）：项目名称去掉两端空白后与本公司 ACTIVE 项目完全相同，工作项标题与该项目中未删除的工作项（含已归档）完全相同。已归档项也参与匹配：历史工时常落在已完成并归档的工作项上，而[导入工作项](../product/2026-10-28-work-item-import.md)按标题去重时不看已归档项，若此处也排除，按提示重新导入工作项会生成重复项。同名的多项中只有一项未归档时取它：已归档的同名项多是重复导入前的原项或早已结束的同名任务，不与仍在进行的那一项竞争。成员还须是该项目的有效成员，否则迁入的工时对本人不可见。找不到、有多个同名或成员不在项目中的行列入 `skippedRows`（`PROJECT_NOT_FOUND`、`PROJECT_AMBIGUOUS`、`WORK_ITEM_NOT_FOUND`、`WORK_ITEM_AMBIGUOUS`、`NOT_PROJECT_MEMBER`），不写入，预览提示先执行工作项导入再重新迁入。原平台的 ID 与 Yumpoo 编号没有对应关系，不参与匹配。
- **只迁入空白日期，整天覆盖**：匹配到的行按成员与日期汇总。成员当天已有自己的计时或补录（含正在运行的计时和跨零点的记录）时，这一天整天不写入，记 `DAY_HAS_TIME`，原有迁入记录也不动；当天只有之前迁入的记录（工作项上的迁入记录或首版 MIGRATED 分类记录）时，先全部删除再写新的，结果是覆盖而不是累加。这次对应不到的行，上次迁入的工时也随这一天清除；没有匹配行的成员日不动。明细表没有「填 0 清除」的写法，接口不再提供清除。同一成员同一天的合计超过 1440 分钟时整次请求返回 422；工作量单位不是「人时」的行在浏览器端报错。
- **排布规则**（按公司时区，不变）：从成员的上班时间（没有设置时取默认 09:00）开始，到当天 24:00 为止，把当天的总时长依次排进空档。排布器按该成员未删除的会话计算已占用时段（正在运行的会话视为占用到当天结束，当天的旧迁入记录除外，比 `min(15 分钟, 剩余时长)` 短的空档跳过）；因为只写入空白日期，实际总是从上班时间起连续排入。排不下的一天记 `NOT_ENOUGH_FREE_TIME`，当天不写入任何记录。末段超过下班时间记警告 `PAST_WORKDAY_END`，日期不早于公司时区今天记 `FUTURE_DATE` 并整天拒绝（计时不能结束在未来），当天原有迁入工时被替换记 `REPLACES_PREVIOUS`。
- **切分**：排出的时段再按文件顺序切给当天的各行（`MigratedTimeLayoutPlanner.split`），一行占连续的一段，或跨空档的几段。排出的总时段与按日总时长排布完全相同。
- **事务与并发**：单事务内按用户 ID 排序依次锁定成员的计时状态，先软删除旧记录再插入新记录，每个成员重建一次份额并推进涉及项目的工时版本。导入只追加记录，不加项目锁。预览与提交共用同一个纯函数排布器。
- **事件与审计**：不发领域事件，整次导入写一条安全审计，内容是汇总数字。
- **失败不动旧数据**：成员无效（`USER_INVALID`）、当天已有成员自己的工时（`DAY_HAS_TIME`）或排不下的一天不写入也不删除，当天原有的迁入工时保持不变。
- **公司时区**：workitem 模块不能依赖 organization，控制器通过 workitem 自己的 `CompanyTimeZonePort` 取公司时区，由 reporting 模块用公司配置实现。

### 回退

V86 只新增带默认值的 migrated 列，属于只扩展迁移，可以快速回退：旧版本忽略该列，迁入到工作项的记录在旧版本中显示为普通补录、成员可以修改，重新升级后恢复只读。以下 V84 的约束不变。

数据库迁移 V84 扩展了 `ck_work_item_time_session_subject` 与 `ck_work_item_time_share_subject` 的取值，属于 breaking 迁移，在 `contracts/migrations/rollback-safety-exceptions.json` 登记例外，晋升到 `main` 的 PR 须加 `release:breaking-migration` 标签。回退到旧版本前必须先删除 `time_category = 'MIGRATED'` 的会话与份额记录，否则旧版本解析枚举会失败。

恢复演练采用[部署手册](../../../../deployment/windows/RUNBOOK.md#1-github-release-自动发布)规定的完整恢复路径：先保留升级后的数据库及附件，再将升级前一致备份恢复到独立空目标，并使用对应的旧发布包验证。恢复到备份时间点意味着之后的业务写入不在恢复结果中，必须先停止写入并由发布负责人决定如何保留、核对和重放这些数据；删除迁入记录不能替代完整恢复验证。晋升标签只确认破坏性迁移及恢复准备，不会使 Server Rollback 绕过版本元数据限制。

`TimeCategory` 响应枚举的扩展会被 openapi-diff 判为不兼容，已在 `tools/openapi/breaking-change-exceptions.json` 按精确哈希登记，本记录是它的依据。

发布级例外以 `server-v2026.10.24.3` 的 main 规范为基线。对完整晋升规范仅在临时副本移除 `TimeCategory.MIGRATED`，openapi-diff 2.1.6 全量检查通过，确认不兼容项仅为该响应枚举扩展；既有开发基线例外保留，新增 main 基线的精确哈希对，不泛化豁免枚举变化。桌面 1.1.3 的原生计时状态 IPC 只接收标题、会话与工作项标识，不解析工时分类；业务页面从服务器加载并识别只读的迁入工时。项目侧栏的新壳能力由桌面 1.1.4 交付，与此 API 枚举兼容性分开处理。

2026-10-29 起迁入请求改为明细行，契约破坏同样按精确哈希登记在 tools/openapi/breaking-change-exceptions.json（2026-10-29-migrated-time-work-items），本记录是它的依据。

## Alternatives considered

- **在现有分类上加「来源」标记而不新增枚举值**：不需要 CHECK 与枚举扩展，但所有读写路径都要多一个条件判断，只读规则也要散落在各处；而新增分类可以直接复用分类这一套已有机制。（这是首版的取舍；2026-10-29 起迁入记到工作项上，工作项记录没有分类可用，只读规则改由独立的 migrated 标记承担，见上文「记录」。）
- **独立的迁入工时表**：与份额分摊、GAPS 空档和各类报表要重复一套读取逻辑，团队工时表也要多一路合并。
- **以成员本人身份写入普通分类**：成员能修改或删除这些记录，也无法区分是否为迁入数据，重复迁入时无法精确覆盖。
- **只写日汇总、不排时段**：现有统计依赖时段，要另建日汇总读取路径，并绕过 GAPS 与重叠校验。
- **允许超过当天的排布（跨日顺延）**：会把工时写到没有给出的日期，所以排不下的一天直接报错，不写入。
- **继续写 MIGRATED 分类、只按所属项目关联**：不需要新列，但工时不进项目统计和工作项工时，明细里的工作项信息被丢掉。
- **对应不到的行改记为 MIGRATED 分类**：用户选择只提醒、不迁入；先导入工作项再重新迁入，避免同一份工时一部分在工作项上、一部分在分类上。
- **在前端匹配项目与工作项**：要把全公司项目与工作项标题下发到浏览器；后端按项目一次取出未删除工作项的标题与归档状态（`WorkItemRepository.findTitles`，与导入工作项排除已归档项的 `findImportTargets` 分开），预览与提交也能共用同一套匹配。
- **按「成员 × 日 × 工作项」覆盖，保留对应不到的旧记录**：不会因项目归档等原因清掉上次迁入的工时，但某行改对应到别的工作项时，旧记录与新记录重复计入，首版的整天记录也可能只被部分替换；迁入记录没有删除入口，无法纠正。用户选择只迁入空白日期、整天覆盖。
- **当天已有成员自己的工时时绕开已有记录排入空档**：迁入的历史合计会与成员在 Yumpoo 里记的同一天工时叠加或重复，无法判断哪一份可信，所以整天不写入。
- **新增 `source='MIGRATED'`**：要放宽 V51 的 CHECK，属于破坏性迁移；独立的布尔列是只扩展迁移。
- **读取汇总表**：只有每日合计，无法分到工作项；明细表已包含全部信息，汇总表忽略。

## Consequences

- **时段是虚构的**：排出的时段只是为了复用现有统计，不代表实际工作时间，所以界面必须标注；其间也会占用成员当天的空档，后续补录的 GAPS 不会再落在这些时段里。
- **回退成本**：V86 可以快速回退；V84 的破坏性约束不变，回退到 V84 之前的版本仍须先清除迁入的分类记录。
- **不留动态**：迁入不发领域事件，也不进入项目活动或「我的动态」，追溯只能看安全审计。
- **项目口径**：迁入到工作项的工时计入项目统计、工作项工时与团队「项目工时」；首版的 MIGRATED 分类记录仍按分类口径，不计入项目统计。
- **覆盖粒度是整天**：不支持只改某一段，需要调整时重新导入当天的工时。重新迁入时，这次对应不到的行（例如项目已归档、成员已离开项目），上次迁入的工时会随这一天清除，预览以「覆盖原有迁入工时」提示原有小时数；没有匹配行的日期不会被清除。
- **已记录的日期不迁入**：成员已在 Yumpoo 计时或补录过的日期整天跳过，即使只有几分钟；需要迁入时，由成员先删除自己当天的记录。
- **可见范围与清除**：迁入只写到成员所在的项目，成员在「我的工时」和「我的一天」能看到；项目永久清除时，迁入到其中的记录随项目一并删除。
- **相关记录**：本记录扩展[非项目固定分类工时](2026-10-22-non-project-time-categories.md)，其余约束不变；工作项部分见[导入工作项](../product/2026-10-28-work-item-import.md)。
