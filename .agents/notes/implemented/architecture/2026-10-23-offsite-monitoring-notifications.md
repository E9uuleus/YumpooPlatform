# Agent Note: 异机监控、维护窗口与可信发布公告

Status: implemented

## Problem

应用内运维中心依赖业务进程与数据库身份校验，无法在两者故障时提供独立观测。GitHub 与 Windows 的单点 Webhook 直发既不能持久重试，也不能证明用户实际访问到新版本。维护期间完全关闭采样会掩盖故障，单凭部署成功又可能公告尚不可访问的版本。

本记录部分替代[单实例运维中心](2026-09-26-operations-center.md)关于外部监控延期的范围；原有采样隔离、数据库分钟历史、规则和受控日志职责继续保留。[诊断安全边界](../security/2026-09-26-operations-diagnostics-access.md)仍约束应用内日志、会话与角色校验。

## Decision

Ubuntu 使用独立 Compose 项目运行 Prometheus、blackbox_exporter、Alertmanager、Grafana、node_exporter 与通知服务。通知服务采用 Node 24、Fastify 5 和 Node 内置 SQLite，界面为独立 Vue 3 工作区。选择内置 SQLite 避免多平台原生扩展编译；运行时与镜像均锁定，WAL/FULL 同步承载事件和投递。组件内存上限合计 1312 MiB，指标保留 30 天或 10 GB，已完成事件/投递保留 180 天。监控升级不随业务 Release 重启。

所有监听在回环地址。管理员通过 SSH 转发访问独立账号，管理 API 采用会话、CSRF、登录限流与审计。机器事件入口和 UI 分端口；Windows 与 GitHub 使用不同 SSH 账号、密钥与 HMAC 来源权限。`MaxSessions 0` 和精确端口允许列表禁止 shell、SFTP 以及转发管理页面。管理员路径不进入成员通知，公网域名与 HTTPS 属于后续开放条件。

应用 `/actuator/prometheus` 是固定指标的只读出口：仅访问已发布的内存采样与规则缓存，不查询数据库、扫描日志或暴露路径/账号。应用、I/O 和规则评估分别提供新鲜度时间。CPU/磁盘告警归主机 exporter，其他应用告警复用已有规则；数据库失联导致规则无法持久化时，用内存连续失败计数补充外部告警。Windows SSH 仅转发 Nginx 的两个固定 metrics 路径，不暴露整个应用监听端口。

外网每 30 秒探测首页、动态发现的关键资源、健康、版本、预期 401 认证入口、下载页、更新清单与安装包。持续访问失败 90 秒通知运维，5 分钟后通知公告群；连续正常 60 秒确认恢复。采集缺失、过期或进程重启中断连续窗口，不补零、不自动恢复。Alertmanager 的 resolved 事件在来源新鲜度不足时持久等待复核；维护抑制中的告警也保留，以便维护结束后重新判断。

Hub 导出低基数的服务展示状态、实际观测状态和维护窗口指标，Grafana 与独立状态页同源，维护中的实际异常仍可辨认。看板由脚本生成，主机告警表达式与阈值以 `tools/monitoring/expressions.mjs` 为单一来源，并由 CI 强制校验，避免看板与告警漂移。`service:probe_success:min` 记录规则按服务聚合探测结果，用于长时段可用率。Windows 磁盘告警只统计盘符卷，排除恢复分区；采集正常但关键服务指标消失时单独告警，避免把缺失当成运行正常。

Windows 前置检查通过后，本地原子落盘维护预告并等待 300 秒；通知失败仍等待并执行。旧配置默认关闭。回退与恢复不等待，桌面更新不进入维护。实际维护事件建立最多 30 分钟的自动窗口，只抑制明确关联的预期应用故障，采样与中断历史继续保留。超时或 `recovery_required` 解除静默。手工维护只管理公告与窗口，不控制主机，自动维护只读。

主机事件与中心待发送消息同事务提交后才 ACK。请求阶段单调前进，迟到的维护事件不能覆盖终态；人工恢复使用独立的 `deployment.recovered` 高阶事件。主机成功还须异机健康与目标 tag/commit 一致，桌面更新还检查清单与下载可达。回退仅公告实际恢复版本；复核失败只通知运维，不改变部署结果或触发数据库恢复。发布说明复用既有 Release/更新清单；运维条目只进运维群。

Windows relay、隧道与看门狗是三个独立监督任务，不执行网络请求于部署锁内。看门狗分别判断事件入口存活和 Prometheus / Alertmanager 的采样新鲜度，避免告警链路自身停止后无人通知；失联或链路异常持续 3 分钟可直接通知运维群，每小时最多重复一次，链路恢复需连续新鲜健康 60 秒。事件入口仍可在采集故障时落库。Grafana 的回环 metrics 也由 Prometheus 监测。GitHub 使用短时事件隧道、三次有界重试；未 ACK 的失败写工作流摘要，不声称持久送达。启用中心后不回退旧直发以免重复。

消息按实际机器人地址限流 15 次/分钟，两个逻辑通道可临时共用机器人。检查 HTTP 与 `errcode=0`，正文按 UTF-8 字节约束，退避到最多一小时，失败队列可人工重试；过时预告和已恢复故障的旧重试会终止。过期失败消息转为 `expired`，不再计入失败积压；人工放弃失败消息转为 `abandoned` 并记录审计，避免已失去发送意义的消息持续触发告警。机器人 URL 从仓库外受保护文件读取，可热更新；管理 API 不返回凭据。

## Alternatives considered

- 只在主站内增加页面和 Webhook：故障域不独立，无法覆盖业务进程、数据库和整机失联。
- 用监控产品的非稳定内部 API 承担发布流程：增加版本耦合，采用标准 Prometheus/Alertmanager 职责与小型持久通知服务。
- 每次抓取查询数据库或沿用应用管理员 API：数据库不可达时失去观测，且引入业务身份依赖；采用低基数内存出口与网络边界。
- 直接转发整个后端端口：机器密钥会获得无关接口能力，改用精确只读网关。
- 通知失败阻止发布：管理员明确选择继续执行；保留 5 分钟等待和失败记录，避免紧急恢复依赖外部机器人。
- 仅凭主机结果公告成功、或由外部监控自动回滚：无法区分实际可见状态与已经发生的数据写入；采用异机复核但不改变主机事实。
- 将所有维护告警全部静音或把未知当正常：会掩盖独立故障与采集失联，采用限时、服务限定的抑制及显式未知。
- 在 Grafana 中手工维护看板：容易与告警规则漂移，无法在代码评审中核对；采用脚本生成与共享表达式、阈值校验。
- 把机器人放入业务数据库、复用业务通知消费者：监控受同一故障域影响，也扩大群公告的数据范围；保持独立配置与队列。

## Consequences

需要单独维护监控账号、密钥、镜像和持久数据，不能把部署代码、实际启动及 24 小时连续验收混为一谈。业务备份和个人通知不在此系统范围。两台机器同时失联仍是盲区；机器人不提供幂等键，远端发送成功但本地落盘前宕机可能重复，整体是至少一次投递。

Node SQLite 接口在锁定运行时仍有实验性提示，升级 Node 时必须重跑持久化、重启和投递测试。管理页当前依赖 SSH，不是公开状态站点。离线镜像包以归档 SHA-256、锁定来源和加载后的镜像 ID 校验；不使用不明来源的镜像加速站替换官方内容。
