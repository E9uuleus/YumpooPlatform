# Agent Note: 本地托盘菜单与主进程退出协调

Status: implemented

## Problem

托盘菜单依赖在线页面，启动和断网时退回另一套原生外观。退出获准后，快捷工时小窗关闭回调会同步已关闭的侧边栏并重建窗口；同时，收到退出请求的回执即取消超时，随后网络请求挂起会永久阻塞退出。

## Decision

本记录部分替代[桌面计时界面](../product/2026-09-24-desktop-timer-surfaces.md)的菜单加载和主题同步方式，以及[计时工作选择器](../product/2026-09-08-timer-work-picker.md)的退出协调方式。界面、定位、键盘操作与计时业务仍由原记录负责。

同一 `TimerQuickMenu` 经独立 Vite 入口打包到桌面安装包；图标、字体与主题随包提供，不初始化认证、路由或业务请求。安装时即预热，首次打开等待组件挂载并推送最新状态。启动显示「启动中」，断线显示连接状态，诊断、更新和退出不依赖业务页。只有本地页面加载失败、超时或崩溃才使用原生应急菜单。

菜单使用诊断页的本地协议及隔离会话，资源保持精确白名单；专用 preload 只暴露菜单状态、动作和通知偏好。IPC 校验所属窗口、主框架和精确本地 URL；不暴露认证、文件或任意 IPC 能力。Web 主窗口经可选桥发布主题和密度，主进程校验后缓存在桌面偏好中；启动使用缓存，首次跟随系统。旧壳仍可使用在线 `/timer/menu`，旧 Web 无阶段桥时继续采用有界退出握手。

`ExitController` 维护唯一请求标识及 checking/prompt/saving/fallback/quitting 状态。回执不能解除 30 秒保护；检查与保存限时，用户选择不计时。启动尚未发布状态、主页面导航、崩溃或无响应时转本地「取消退出／继续计时并退出」确认。进入 fallback 先取消 Web 确认，迟到阶段与完成不能改变已作出的选择。取消后尚未发送的停止命令不得继续发出；已发送的请求可能已由服务端执行，不把超时当作保存成功。

批准时先标记 quitting，取消偏好订阅和定时器，依次停止侧边栏、快捷小窗、菜单与浮窗，再正常 `app.quit()`。停止可重复调用，所有创建、预热和显示入口检查停止状态，保留 `will-quit` 更新安装和偏好落盘流程。主窗口右上角关闭仍只隐藏。

## Alternatives considered

- 继续在线菜单并美化原生备用：离线和冷启动仍不能获得一致界面，未解决加载依赖。
- 复制一套 HTML 菜单：容易使功能、图标与主题分叉，选择独立入口复用原组件。
- 强制结束进程：跳过正常退出的偏好落盘及更新安装，不符合现有交付契约。
- 全程固定超时：用户正常思考也会触发备用确认，因此区分用户选择和网络等待。
- 收到回执就认为退出正常：回执只证明事件到达，不能证明后续检查或保存完成。

## Consequences

该修复需要重建并升级桌面客户端；仅部署 Web 无法修复窗口生命周期或替换旧壳菜单。独立菜单增加桌面资源和依赖清单，构建合并许可证与 SBOM，ASAR 检查包含新增资源和 preload。业务窗口仍在线，不增加离线业务能力。本地确认仅允许取消或明确继续计时，保存结果不确定时由用户重新打开核对。

## Verification

退出控制器覆盖阶段超时、取消、迟到回复、重复请求和页面失效；窗口测试覆盖停止后的预热和加载回调。`node tools/verification/desktop-lifecycle-smoke.mjs` 使用独立临时配置、回环页面和真实 Electron 控制器，检查冷启动、断网三主题、关闭次序及批准后五秒内全部进程结束；运行前需构建桌面包。启动场景只替换本地确认的用户选择，不跳过退出协调或真实窗口销毁。
